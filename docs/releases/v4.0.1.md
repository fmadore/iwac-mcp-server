# v4.0.1: Semantic search no longer stalls the server

v4.0.0 ran the query encoder on the server's main thread. onnxruntime-node
executes `session.run` synchronously on the calling thread, so every semantic
search froze all other requests for the length of the encoding (about 0.5 s on
the development laptop), and the first search of a subset froze them for up to
2.8 s while its index was built. On a shared endpoint every user would feel that.

- **The encoder runs in a worker thread.** The session, the tokenizer and every
  encoding live there; the main thread only exchanges messages with it. MCP
  pings sent during a warm semantic search now answer in 2 to 8 ms, against up
  to 620 ms before.
- **Index builds yield.** A subset's vectors are read from DuckDB one chunk at a
  time and normalised straight into the index with regular yields to the event
  loop, instead of being converted in one synchronous pass. During the first
  article search (16,668 vectors) the slowest concurrent ping drops from
  2.8 s to 0.12 s.
- **One CPU thread per encoding by default**, configurable with
  `IWAC_EMBEDDING_THREADS`. onnxruntime's default is every core, which
  oversubscribes a CPU-capped container: on q8, 1 thread took 550 ms of wall
  time for 500 ms of CPU, 4 threads ~400 ms for 1,100 to 1,400 ms. The thread
  pool also sleeps between queries instead of spin-waiting.

Query vectors are unchanged: the parity test still gives identical token ids
and cosine 0.999942 (q8) and 1.000000 (fp32) to the Python reference. Memory,
measured under a 512 MB V8 heap cap: about 75 MB resident idle, under 800 MB at
peak with the encoder and all four semantic indexes loaded.
