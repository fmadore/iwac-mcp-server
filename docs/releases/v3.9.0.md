# v3.9.0: Read long texts whole

Full texts longer than 25,000 characters can now be read to the end, not only
searched for excerpts.

- **Full text in parts.** `get_article`, `get_document`,
  `get_publication_fulltext` and `get_audiovisual` take an `offset`. A part
  that stops short of the end reports `char_count` and `next_offset`; passing
  `next_offset` back returns the next part, until the last. Until now,
  everything past the first 25,000 characters was reachable only through
  keyword excerpts: three in four publication issues (up to 1.1M characters),
  the longest sermon transcriptions (~470k) and a few documents and articles.
  Against the real dataset, the longest transcription reads in 19 parts and the
  longest issue in 45, with no gap or overlap.
- **Around the parts.** When `fetch` cuts a text, it names the tool and the
  offset to read on from. An issue's table of contents comes with its first
  part only. An offset past the end returns a note instead of an empty text,
  and an offset passed beside a `keyword` is reported as ignored.
- **Smaller tool footprint.** Tool definitions no longer advertise the
  safe-integer bounds zod writes on every integer field. That saves about
  1,200 tokens: the always-on footprint drops from 15,811 to 14,815 tokens,
  paging included. Argument validation is unchanged.
- **Release guard.** The read-only check that runs before publication now
  retries timeouts and server errors (4 attempts, with backoff) and names the
  lookup that failed. v3.8.0 stopped there on a single MCP Registry timeout and
  was published by re-running the job.

The research skill documents how to read a long text whole and what it costs
(6 to 8k tokens per part), and asks the model to confirm before reading more
than a few parts.
